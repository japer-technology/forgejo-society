# Full Stack AI

## MCP + AI Gateway + A2A: the emerging enterprise agent architecture

The image is not merely a systems diagram. It is an argument about how serious AI agent platforms should be built. Its central claim is that **MCP, an AI Gateway, and A2A solve three different but complementary interoperability problems**. MCP connects agents to tools and enterprise systems. The AI Gateway governs access to models, tools, agents, policies, costs, and telemetry. A2A lets one agent communicate with another agent without needing to know its internal implementation. Together, they form a controlled, observable, multi-agent enterprise fabric.

At the top of the diagram, the user issues a natural-language request. That request enters an **Agent Application / MCP Host**, which is the local orchestration environment. In MCP terminology, the host is the AI application that initiates connections, the client is the connector inside that host, and the server is the external service exposing context or capabilities. MCP’s architecture uses a JSON-RPC data layer and a transport layer, with core primitives such as tools, resources, prompts, notifications, and lifecycle management. ([Model Context Protocol][1])

Inside the agent application, the work is decomposed into specialised internal agents: a planner, retriever, summariser, and executor. This is the “thinking and doing” layer. The planner decides what needs to happen. The retriever gathers relevant data. The summariser compresses or interprets it. The executor performs actions. Beneath them sit two important client layers: the **MCP Client Layer**, used to call tools and systems through MCP servers, and the **A2A Client**, used to communicate with external agents.

The bottom of the image shows the MCP side of the world: Jira, Confluence, internal APIs, custom backends, and Dynatrace are exposed through **MCP servers**. This is the tool-and-context plane. MCP standardises how an agent asks a system for data or actions, instead of every agent needing a custom integration for every backend. The MCP Registry or Catalog is labelled “discovery only,” which matters: it is not the execution layer. It is the directory where available MCP servers and their metadata can be found. Execution still happens through authenticated MCP requests to the relevant server.

The right side shows the A2A side of the world: a **Remote A2A Agent** with an agent card, messages, tasks, streaming, and artifacts. This is the agent-to-agent plane. A2A exists because not every capability should be reduced to a tool call. Sometimes the external system is itself an autonomous or semi-autonomous agent with its own model, tools, memory, workflow, and policies. The official A2A specification describes it as an open protocol for communication and interoperability between independent, potentially opaque agent systems, allowing agents to discover capabilities, negotiate modalities, manage collaborative tasks, stream updates, and exchange information without exposing internal state or tools. ([A2A Protocol][2])

The centre of the diagram is the key architectural decision: the **AI Gateway** sits between the agent application, model providers, remote agents, identity systems, observability, and MCP infrastructure. It is the policy enforcement and traffic mediation point. Its functions include routing, security, policies, rate limits, monitoring, unified model access, and tool-and-agent governance. This is why the gateway is drawn as the operational hub rather than as a passive proxy.

The AI Gateway’s connection to LLM providers shows another important meaning: the agent application should not be tightly coupled to OpenAI, Anthropic, Gemini, or a domain-specific model. A gateway can expose a unified model API, route requests to different backend providers, translate formats, manage aliases, handle failover, and apply policies consistently across providers. Microsoft’s AI Gateway documentation describes this exact pattern: managing multiple model backends, securing and governing AI models, agents and tools, supporting OpenAI, Anthropic and Google-style APIs, and exposing multiple backends through a single unified API. ([Microsoft Learn][3])

The purple observability and audit block on the left is not decorative. It represents the accountability layer required for production agent systems. Tracing, logs, metrics, usage, cost, replay, and audit are essential because agent behaviour is not a single deterministic API call. It is a chain of decisions, retrievals, model calls, tool invocations, remote-agent messages, and final actions. OpenTelemetry’s LLM observability guidance highlights the need to track traces, metrics, request parameters, model versions, token usage, latency, cost, and the sequence of events around LLM calls. ([OpenTelemetry][4])

The identity and authorisation block on the lower right shows that this architecture is meant for enterprise deployment, not hobby experimentation. Access tokens flow to MCP servers, A2A agents, model providers, and the gateway. Identity providers such as Microsoft Entra ID and Okta sit behind the access model. MCP’s authorisation specification aligns with this pattern by treating protected MCP servers as OAuth-protected resources and recommending scoped access tokens and least-privilege authorisation flows. ([Model Context Protocol][5])

The diagram’s deepest point is governance. The AI Gateway is not only routing model calls; it is governing **models, tools, and agents together**. That is the new enterprise control problem. Traditional API gateways governed deterministic services. LLM gateways initially governed model calls. But agentic systems require governance over tool invocation, agent delegation, identity, prompt flow, artifacts, streaming, cost, rate limits, and auditability. The image is therefore showing a shift from “call an LLM” to “operate an AI workforce.”

The red, blue, green, and purple arrows reinforce this division of responsibilities. Blue paths represent request/response and MCP execution flows. Green paths represent discovery and model API calls. Red paths represent A2A communication. Purple paths represent access tokens, identity, observability, and audit. The point is that an enterprise agent platform is not a single pipeline. It is a mesh of different protocols, each with different trust boundaries.

In practical terms, the user asks a question; the host agent plans the work; the retriever may query Jira or Confluence through MCP; the executor may call an internal API MCP server; the gateway may route model calls to OpenAI, Anthropic, Gemini, or a specialist model; the A2A client may delegate part of the task to a remote agent; identity systems issue scoped tokens; the observability layer records what happened; and the gateway enforces policy across the whole process.

The image also implies what can go wrong. Without the gateway, every agent becomes its own security boundary. Without MCP, every tool integration becomes bespoke. Without A2A, agents cannot collaborate cleanly and must impersonate tools or APIs. Without observability, no one can explain cost, latency, data movement, or action history. Without identity, agents become overpowered automation scripts. Without a registry, agents cannot discover capabilities in a controlled way.

So the full meaning is this: **MCP gives agents hands, A2A gives agents colleagues, and the AI Gateway gives the enterprise a control tower.** MCP standardises access to systems. A2A standardises agent collaboration. The AI Gateway centralises governance, routing, policy, security, monitoring, and cost control. The architecture turns fragmented AI experiments into a managed agent platform suitable for real operational use.
